# tylpet 3D 空间交互桌面统一方案

> 文档状态：四份方案合并定稿草案。来源：3D交互桌面设想.md、3D交互桌面方案v2.md、3D空间交互桌面完整方案.md、3D空间桌面视觉与展示方案.md。
> 核心方向：Blender 视口网格 + 番剧风 VRM + 米塔式 3D 悬浮文字，构成轻量、透明、可交互的桌面陪伴空间。

## 1. 一页结论

将当前 2D SVG 桌宠升级为桌面上的透明 3D 空间伙伴：桌面底部横贯 Blender 建模视口风格的地面网格；右下偏右站立一个现成开源 VRM 角色；角色使用番剧风 MToon 和三点工作室布光；鼠标靠近时才唤醒注视和交互；说话时生成 3D 文字，结束后文字落到网格上弹跳并消散。

### 统一基线

| 主题 | 结论 |
| --- | --- |
| 空间 | Blender 视口地面网格，第一版不做写实房间 |
| 窗口 | 第一阶段为独立全屏 Tauri 游戏；后续再适配透明桌面模式 |
| 角色 | 第一阶段使用授权清晰的现成开源 VRM |
| 相机 | 固定透视相机，俯角 12°~15°，FOV 约 38° |
| 构图 | 角色位于屏幕右侧偏右下，横向 75%~80%，高度约 45%~50% |
| 渲染 | Three.js + @pixiv/three-vrm + MToon；首版不做真 Bloom |
| 交互 | Rust 获取物理光标并控制整窗穿透；Web 层不负责把事件还给桌面 |
| 状态 | Dormant / Ambient / Aware / Engaged / Focus |
| 动作 | 招手、专注坐下、小憩 |
| 文字 | 3D 悬浮打字 → 重力坠落 → 网格碰撞 → 粒子消散 |
| 门禁 | 先验证性能和穿透；失败则降级为小窗 3D 桌宠 |

### 第一版不做

1. 写实房间、墙面、书桌和窗户等大体量资产；
2. WorkerW 桌面壁纸层注入；
3. 真 Bloom、复杂全屏后处理和高成本实时阴影；
4. 多房间、场景编辑器、手部 IK 和复杂路径行走；
5. 未完成授权审查的角色素材；
6. Unity / Unreal 重写渲染层；
7. 多显示器完整适配，首版先保证主屏。



## 2. 产品愿景与世界模型

> 本节记录后续讨论确认的产品方向。它将原方案中的“3D 桌宠”升级为“异世界观察窗口”，是后续世界包、角色行为和创意工坊设计的上层约束。

### 2.1 产品定位

tylpet 不再只被定义为一个带 3D 角色的桌面宠物，而是一个运行在电脑上的**异世界观察窗口**：玩家通过屏幕观察另一个空间中的角色，与她建立有限但持续的联系。桌宠只是其中一种角色形态，不是产品边界。

核心使用循环是：


打开世界 → 观察角色生活 → 鼠标靠近或触碰屏幕 → 角色察觉并回应 → 玩家继续观察

默认关系如下：

- 玩家是观察者，不直接操纵镜头；
- 世界在没有用户操作时仍然存在；
- 角色以轻度自主方式进行自己的日常活动；
- 玩家通过屏幕、鼠标和消息与世界建立联系；
- 角色从一开始就知道屏幕后面存在用户。

### 2.2 第一阶段的显示形态

第一阶段先作为一个独立的全屏游戏运行，不直接作为 Windows 桌面壁纸层实现。玩家画面被定义为异世界中一块悬浮屏幕的另一侧视野：

- 玩家通常看不到悬浮屏幕的正面；
- 角色可以看到、靠近、注视、触碰或敲击这块屏幕；
- 屏幕本身显示半透明空白内容，不实时捕获用户桌面，也不读取桌面像素；
- 鼠标和聊天消息被转换为角色能够理解的用户信号；
- 角色对屏幕的行为反过来证明异世界与玩家之间存在连接。

这一定义暂时取代“透明窗口直接叠加在桌面上”作为第一阶段的主要产品形态。未来仍可将同一世界运行时适配到透明桌面模式，但不应提前把两种窗口形态混为一个实现目标。

### 2.3 用户信号与屏幕触点

第一阶段角色可感知三类用户信号：

| 信号 | 异世界表现 |
| --- | --- |
| 鼠标位置或靠近屏幕 | 屏幕上出现可被角色追踪的光点 |
| 鼠标点击屏幕 | 产生触点、波纹或敲击反馈，角色可被唤醒或打断 |
| 独立聊天窗口消息 | 角色转向屏幕，并以动作、3D 悬浮文字和 TTS 回应 |

光点和触点首版对玩家与角色都可见。用户消息继续使用现有独立 ChatWindow 作为输入入口，异世界负责动作、视线、3D 文字和语音回应。

### 2.4 两种世界模式

所有内容统一称为 **World Pack（世界包）**，由包内声明运行模式：

#### editable-grid：可运行时布置的 Blender 无限网格世界

- 视觉上向远处无限延伸，实际活动区可以有限；
- 程序化生成网格、坐标轴、透明背景和活动区域；
- 用户可以从创意工坊放入物件，并进行位置、旋转和缩放等基础变换；
- 角色可以在活动区内生活，并使用声明过的物件；
- 这是第一阶段的默认世界，也是平台运行时布置能力的主要验收样本。

#### authored-scene：作者预制的完整场景世界

- 作者在 Blender 或其他外部工具中完成场景布局后导入；
- 运行时不能随意添加新物件，也不能自由改动场景布局；
- 角色可在作者定义的活动区、路径或交互点之间自主移动；
- 物件的位置和可用能力由作者预先声明；
- 适用于房间、观测站、庭院等完整创作型世界。

这两种模式必须在用户界面和资产协议中明确区分能力边界，避免用户误以为所有场景都可以自由编辑。

### 2.5 创意工坊的第一阶段入口

第一阶段采用“外部工具制作 + 资产包导入 + 运行时有限调整”，暂不开发完整的内置世界编辑器。World Pack 可包含以下模块：

- 角色；
- 场景地图；
- 物件；
- 镜头；
- 光线与天气；
- 行为与生活规则。

在 editable-grid 世界中，用户可以运行时放置工坊物件；在 authored-scene 世界中，用户只能使用作者预先放置并声明的物件。两种模式都支持角色在作者定义或平台提供的活动区域内自主生活。

### 2.6 角色活人感的首阶段原则

用户希望角色具备持续日常活动、环境感知、偶尔主动反应、记忆连续性和自主改变环境的能力。第一阶段优先保证前两项体验：

1. 角色在没有用户操作时仍有持续的日常活动；
2. 角色会偶尔主动发现用户、看向屏幕或做出简短回应。

行为生成采用“**作者预设活动骨架 + AI 小范围变体**”模式：

- 作者定义活动、时段、地点、可用物件和打断规则；
- AI 负责台词、表情、少量目标选择和活动中的小变化；
- 不允许 AI 无约束地决定场景结构、任意生成物件行为或绕过权限执行动作；
- 角色行为采用分级打断：靠近只引起注意，点击和明确消息才产生更高优先级回应。

首阶段首要验证的是“她在生活”，而不是“她拥有完整自主意识”。

### 2.7 世界、角色与身份暂定关系

世界状态与角色身份暂时分离保存：

- **角色档案**：角色名称、性格、关系、记忆和可迁移偏好；
- **世界存档**：当前世界、活动进度、物件状态、环境状态和事件记录；
- **当前组合**：正在使用的角色、场景、物件、镜头和光照资产。

更换角色模型时，第一阶段默认将其视为新角色；用户可以明确选择继承旧角色的部分记忆。继承范围优先支持称呼、偏好、关系摘要和羁绊等级，不直接迁移完整聊天记录。

该身份模型仍属于后续需要继续细化的设计项，但不得把所有记忆简单绑定到 VRM 文件或某一个场景包中。

### 2.8 首个世界验收样本

第一阶段使用“Blender 无限网格中的独立角色”作为平台验收世界：

- 程序化无限网格作为空间底座；
- 角色在有限活动区内轻度自主生活；
- 场景中存在统一的半透明用户屏幕锚点；
- 用户可通过光点和点击触碰屏幕；
- 用户可从创意工坊放入少量声明过的物件；
- 角色能够在日常活动中识别并使用这些物件；
- 固定观察镜头为默认镜头，重要事件允许切换作者提供的预设镜头；
- 对话通过独立 ChatWindow 输入，角色以动作、3D 文字和 TTS 回应。

### 2.9 第一阶段暂不承诺

在独立全屏游戏阶段，暂不承诺以下能力：

- 实时显示用户真实桌面或当前窗口；
- 读取或重绘 Windows 桌面图标；
- 让角色直接操作真实桌面文件、图标或应用；
- 完整的用户自由镜头控制；
- authored-scene 世界的运行时自由摆放物件；
- AI 完全自主制定长期日程或改变世界结构。

## 3. 改造边界

3D 改造只替换渲染层、空间交互层和窗口层，保留全部业务能力：

| 现有模块 | 策略 |
| --- | --- |
| src/domain/chat、src/providers、src-tauri/src/chat.rs | 保留 AI Provider、流式对话、Mock、SSE 和取消机制 |
| src/domain/memory、src-tauri/src/memory.rs | 保留长期记忆、摘要、羁绊和恢复能力 |
| TauriTimerController、src-tauri/src/timer.rs | 保留可靠番茄钟，开启时驱动 Focus |
| src/domain/observations、src-tauri/src/plugins.rs | 保留观察事件和插件安全边界，可增加受限 scene.* 请求 |
| TTS、托盘、设置、退出路径 | 保留；增加 3D、性能和状态选项 |

新增内容：全屏透明窗口、动态穿透、Three.js 场景、Viewport Grid、VRM 角色、Raycaster、注意力状态机、3D 浮空文字和掉落特效。

## 4. Blender 视口地面网格

### 3.1 视觉规则

放弃会遮挡壁纸和图标的实体房间，使用半透明、镂空的 3D 建模工作台。网格横贯屏幕底部，向上和两侧平滑淡出，网格之外完全透出原生桌面。网格永远不消费鼠标事件，角色脚底设置接触投影。

### 3.2 首轮参数

| 参数 | 值 |
| --- | --- |
| 普通网格线 | RGBA (255,255,255,0.15)，约 1 CSS px |
| X 轴 | #EB4034，横向贯穿底部 |
| Y 轴 | #43B549，从原点向景深延伸 |
| 原点 | 角色脚底附近，屏幕右下偏中 |
| 衰减 | 向上从约 0.2 平滑到 0，两侧径向淡出 |
| 实现 | 优先程序化 Shader 或有限线段，不使用大地面模型 |

接触阴影使用羽化的半透明椭圆面片，随站姿、坐姿和角色位置更新。文字坠落的碰撞面统一为地面 y = 0。

## 5. 相机、构图与 VRM

- 相机使用 PerspectiveCamera，FOV 首选 38°，允许 35°~38° 调整。
- 镜头固定，俯角 12°~15°，不随鼠标做视差运动。
- 角色水平锚点约为屏幕宽度 75%~80%，脚底靠近网格原点。
- 角色高度约占屏幕 45%~50%，左侧图标区和中央工作区保持低干扰。
- 实际尺寸应根据窗口、DPI 和相机投影计算，不能只写死像素。

第一阶段使用现成开源 VRM 跑通技术链路。必须记录来源、版本、作者和许可证，确认允许本地运行、演示和发布。建议控制在约 2.5 万~3.5 万三角面，收敛贴图和材质数量。

## 6. 番剧三渲二与三点布光

### 5.1 MToon

使用 VRM 0.x 或 1.0 与 @pixiv/three-vrm。ShadeToony 初始目标 0.90~0.95；阴影色使用基底色的冷暖衍生色；面部降低不利于识别的斜射阴影；描边采用 MToon / Inverted Hull 风格细描边，颜色取邻近深色而非纯黑。

### 5.2 工作室三点冷白光

| 灯光 | 位置与色调 | 作用 |
| --- | --- | --- |
| Key 主光 | 前上方，暖白 #FFF8F0，强度约 1.8 | 照亮面部和主体 |
| Fill 补光 | 侧前方，冷蓝白 #D0E0FF，强度约 0.8 | 保持暗部通透 |
| Rim 轮廓光 | 后上方，近白色，强度约 3.0 | 勾勒发丝、肩线和四肢 |

数值是调参起点。第一版不依赖真 Bloom，氛围使用灯光、低成本材质、暗角和 Shader 模拟。

## 7. 动态和注意力状态机

### 6.1 生命感

呼吸约 3.5 秒周期；3~5 秒随机眨眼，偶发双眨眼；SpringBone 只保留马尾、发带、裙摆等关键链条，优先控制在 20 根以内；所有定时器、rAF 和监听必须清理。

### 6.2 近场唤醒注视

- 距离角色超过 300px：目视前方，安静陪伴。
- 进入约 300px：进入 Aware，眼球高权重追踪，头颈以约 40% 权重平滑跟随。
- 离开约 350px：退出 Aware，约 1 秒内回正。
- Focus 状态下不因普通鼠标移动抬头。

### 6.3 五态定义

| 状态 | 触发 | 穿透 | 帧率 | 表现 |
| --- | --- | --- | --- | --- |
| Dormant | 手动休眠或全屏游戏 | 全穿透或隐藏 | 0 | 停止渲染，托盘保留 |
| Ambient | 默认空闲 | 全穿透 | 15 | 呼吸、眨眼、轻微物理 |
| Aware | 光标进入近场 | 关闭穿透 | 60 | 追视、轮廓反馈、准备点击 |
| Engaged | 点击角色或物件 | 关闭穿透 | 60 | 动作、对话、口型、文字特效 |
| Focus | 番茄钟运行 | 全穿透 | 15 | 坐下阅读，低干扰陪伴 |

状态机是窗口和渲染的唯一事实源。插件只能请求语义动作，不能直接绕过状态机控制窗口。

### 6.4 首发动作

1. Wave：点击角色后招手并回应；
2. Focus：番茄钟开始时坐下，结束后起身或招手；
3. Sleep：夜间或休眠前闭眼、低头、放慢呼吸。

动作优先采用社区 VRMA 或 Mixamo 到 Blender 再到 VRM 的重定向方案，逐动作验证骨骼和插件兼容性。

## 8. 3D 浮空文字与重力坠落

角色说话时文字成为空间实体：在身旁逐字浮现，停留约 1.5 秒后向网格下落，撞击 y = 0 地面，阻尼弹跳一次，再化为碎屑粒子消失。

生命周期：生成 → 打字机出现 → 悬浮微晃 → TTS 结束后停留 → 重力坠落 → 网格碰撞 → 粒子消散。

首选 SDF 字体或轻量文本几何；配置字体、字号、字距和最大行宽；长回复需要摘要或分段；设置并发上限、队列和对象回收。第一版口型使用 TTS 响度近似驱动 aa 等 blendshape，后续再接入音素边界。

## 9. 动态穿透与 Windows 交互

Web 层无法把已经消费的鼠标事件可靠还给桌面，因此穿透必须由窗口样式、Tauri 或 Win32 控制。

主路线：

1. 窗口默认透明、置顶、忽略光标事件；
2. Rust 使用 Win32 GetCursorPos 约 30Hz 获取物理坐标；
3. 结合窗口位置、DPI 和 devicePixelRatio 转换为 CSS / NDC 坐标；
4. Three.js Raycaster 只检测角色和当前允许交互的对象；
5. 进入角色包围圆后关闭穿透并进入 Aware；
6. 离开滞回外圈后恢复全穿透。

进入半径约 300px，退出半径约 350px。必须在真实 Tauri 窗口中验证快速甩动、DPI、任务栏、桌面图标和右键菜单。

如主路线不满足手感，再评估 WH_MOUSE_LL；回调必须极短，不能阻塞或执行复杂 IPC。备选仍失败则降级小窗模式。

交互规则：网格空白处左键、右键、框选直达 Windows 桌面；角色左键招手并进入 Engaged；角色右键打开设置、番茄钟、聊天和退出菜单；场景物件只在 Aware / Engaged 开放。

## 10. 性能预算

| 项目 | 目标与策略 |
| --- | --- |
| Dormant | 0fps，停止 rAF，必要时隐藏 |
| Ambient | 15fps，限制 SpringBone 和事件 |
| Aware / Engaged | 60fps，只在近场或交互期间升帧 |
| 像素比 | 不超过 1.25 |
| 显存 | 目标不超过约 400MB，以实测为准 |
| 文字粒子 | 并发上限、队列和回收 |

全屏游戏或前台高负载场景自动进入 Dormant 或低功耗模式。透明窗口、任务栏、图标、右键菜单和其他窗口拖动都属于性能验收范围。

## 11. 架构与目录

建议新增 src/spatial：

- engine：SpatialStage、ViewportGrid、RenderLoopController、LightingRig；
- character：VrmAvatar、LookAtController、MotionDirector、LipSyncDriver；
- fx：FloatingText、GravityDrop、ParticleDissolve；
- interaction：CursorTracker、SpatialHitTester、AttentionDirector。

Rust 负责透明窗口、动态穿透、物理光标、全屏检测、托盘和原生能力。Web 负责 Three.js 场景、VRM、动画、文字和表现。domain 层不依赖 Three.js，空间层只消费业务语义结果。

## 12. 实施路线与门禁

### Phase 0：双 Spike，2~3 天

Spike 1：全屏透明窗口 + Three.js 网格 + 现成 VRM + 三点光，测试 15/60fps、GPU、内存、闪烁、黑块、任务栏和其他窗口拖动。

Spike 2：Rust 30Hz 光标坐标 + DPI 换算 + 300px 近场 + 滞回切换，测试桌面图标、右键菜单、角色点击、快速甩动和延迟。

双通过才进入 Phase 1；性能不通过则终止全屏方案；穿透不通过先尝试备选钩子，仍不通过则小窗降级；止损上限约 3 天。

### Phase 1：角色与网格地基，约 1~2 周

引入依赖，搭建 src/spatial，完成固定相机、网格、接触阴影、VRM、MToon、三点光、SpringBone、呼吸、穿透和 LookAt。

### Phase 2：文字表现，约 1 周

完成 SDF / 文本几何、打字机、悬浮、停留、重力、碰撞、消散、TTS 接入和对象回收。

### Phase 3：五态与动作，约 1~2 周

打通五态，接入 Wave、Focus、Sleep，连接番茄钟、记忆、羁绊，并完成 0/15/60fps 调度。

### Phase 4：验收发布，约 1 周

测试 1080p、2K、100%/125%/150% DPI、长时间运行和资源释放；验证桌面交互；接入最终授权角色；输出发行版和演示视频。按课余投入整体预计约 2.5~3 个月。

## 13. 风险与验收

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 全屏透明性能不足 | 高 | 前置 Spike、降帧、限像素比，小窗降级 |
| 动态穿透不自然 | 高 | 包围圆、滞回、备选钩子、降级 |
| DPI / 多屏坐标错位 | 高 | 物理像素、主屏优先、真实窗口测试 |
| VRM 动画工时膨胀 | 中 | 三动作封顶，社区 VRMA 兜底 |
| 汉字文字性能问题 | 中 | SDF、长度限制、并发上限 |
| 授权或协议不清 | 中 | 记录许可证，不提交未审查资产 |
| 挤占主线时间 | 中 | 阶段门禁和三天止损线 |

最终验收必须包含：网格和空白区完全穿透；角色近场追视；三动作可用；文字浮现、坠落、弹跳、消散；对话、TTS、记忆、番茄钟和托盘仍正常；业务域不反向依赖 Three.js；监听、定时器、rAF 和资源均可释放；不同 DPI 下坐标和构图正确。
